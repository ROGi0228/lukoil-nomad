## 0. Резюме проекта

Telegram-бот для регистрации участников автопробега/путешествия (партнёр — Lukoil, есть медийные участники). Функции: приветствие → регистрация (ФИО/телефон/город) → загрузка фото водительского удостоверения с автоматическим OCR и сверкой → загрузка видео-визитки → модерация администратором → уведомления на всех этапах.

Ключевые нефункциональные требования: мгновенный отклик бота, отсутствие зависаний, работа 24/7, масштабируемость, защита персональных данных, защита от повторной регистрации и спама.

## 1. Архитектура и стек

### 1.1 Выбранный стек

| Слой | Технология | Причина |
|---|---|---|
| Язык | Python 3.12+ | Единый язык для бота, OCR и обработки изображений/видео — не нужно городить отдельный сервис на другом языке |
| Bot framework | **aiogram 3.x** | Нативный asyncio, встроенный FSM (важен для пошагового визарда регистрации), Router-архитектура (естественно ложится на SOLID/модульность), сильное middleware (throttling, логирование, DI сессии БД), большое активное RU-сообщество и документация |
| Web framework (admin API + webhook) | **FastAPI** | Async, автогенерация OpenAPI, легко переиспользовать Pydantic-схемы между ботом и админкой |
| ORM / миграции | SQLAlchemy 2.0 (async) + Alembic | Стандарт де-факто, полный контроль над схемой, безопасные миграции |
| База данных | **PostgreSQL 16** | ACID + уникальные constraints — критично для защиты от повторной регистрации; JSONB для сырых OCR-данных без раздувания схемы |
| Кэш / очередь / FSM-хранилище | **Redis 7** | Хранилище состояний aiogram FSM, брокер задач, счётчики антиспама/rate-limit |
| Фоновые задачи | **arq** (Redis-based async task queue) | OCR-запрос, обработка видео, рассылки — не блокируют event loop бота; легче Celery, полностью async, тот же Redis, что и FSM |
| Файловое хранилище | **S3-совместимое object storage** (MinIO на VPS или облачный S3) | Бот должен быть stateless (для будущего горизонтального масштабирования); диск VPS — не источник истины для медиафайлов |
| OCR | **Yandex Vision OCR / Google Cloud Vision** (текстовый слой) + собственный слой валидации (структура/формат/эвристики) | Специализированный SDK с проверкой подлинности (Smart Engines/Regula) признан слишком дорогим для бюджета проекта — заменён связкой «дешёвый OCR + структурная валидация под образец ВУ РК + финальная проверка модератором глазами». См. раздел 8 |
| Админ-панель (MVP) | Telegram-нативная (админ-режим в том же боте) | Быстро, без отдельного фронтенда, достаточно для старта |
| Админ-панель (V2) | FastAPI + Jinja2/HTMX (без отдельной SPA-сборки) | Быстрее в разработке, чем React SPA, но даёт полноценный веб-интерфейс с фильтрами/таблицами |
| Контейнеризация | Docker + docker-compose | Воспроизводимость, изоляция сервисов, простой rollback |
| Reverse proxy / TLS | Caddy | Автоматический HTTPS без ручной возни с certbot |
| Логирование | structlog → JSON логи (+ опционально Loki/Grafana в V2) | Структурированные логи, трассировка запросов, маскирование PII |
| Мониторинг ошибок | Sentry (бесплатный tier достаточно на старте) | Мгновенное обнаружение падений/зависаний — прямое требование к стабильности |
| CI/CD | GitHub Actions → сборка образа → деплой на VPS по SSH | Автоматизация без ручного деплоя |

### 1.2 Почему не альтернативы

- **PHP / shared hosting** — исключено (см. раздел 6): нет постоянного процесса, нет очередей, нет Redis/Postgres, лимиты времени выполнения ломают OCR-запросы.
- **python-telegram-bot / Telethon** — жизнеспособны, но FSM-эргономика aiogram 3 удобнее именно для мастера регистрации из нескольких шагов.
- **Node.js + Telegraf** — тоже валидный вариант, но пришлось бы либо выносить OCR/обработку изображений в отдельный Python-сервис, либо мириться с более слабой экосистемой CV/OCR в Node. Один язык — меньше точек отказа.
- **MongoDB** — данные принципиально реляционные (пользователь → заявка → лог модерации → уведомления), плюс нужны строгие unique-constraints — Postgres здесь естественнее и надёжнее.
- **Celery** вместо arq — тяжелее (требует отдельного брокера/конфигурации, много синхронного legacy-кода), для async-стека aiogram+FastAPI arq — более естественный выбор.

### 1.3 Плюсы / минусы стека

**Плюсы:** полностью async от бота до воркеров (OCR/видео не блокируют ответы пользователю); stateless-боты можно масштабировать горизонтально за Redis; дешёво в эксплуатации; зрелые, активно поддерживаемые библиотеки.

**Минусы:** требует VPS и базового Docker/DevOps-навыка (выше порог входа, чем shared hosting); Python GIL — CPU-тяжёлые операции (обработка изображений) обязаны идти через воркеры, а не в event loop бота (учтено архитектурой воркеров).

## 3. Модули системы

1. **Telegram Bot Core** — точка входа, роутинг, FSM.
2. **Registration** — сбор ФИО/телефон/город, валидация ввода.
3. **Document Verification (OCR)** — распознавание ВУ, сверка ФИО, проверка формата и уникальности.
4. **Video Intake** — приём видео-визитки, базовая валидация (размер/длительность/формат).
5. **Moderation** — очередь заявок, действия администратора, аудит-лог.
6. **Notifications** — все исходящие уведомления пользователю (статус, новости, активности).
7. **Database** — модели, репозитории, миграции.
8. **File Storage** — абстракция над S3/MinIO, подписанные URL.
9. **Admin Panel** — Telegram-режим (MVP) → веб-панель (V2).
10. **Auth (Admin)** — роли admin/moderator, доступ по Telegram ID (MVP) → логин+2FA (V2).
11. **Antifraud/Antispam** — rate-limiting, дедупликация, проверка уникальности документа.
12. **Logging & Monitoring** — structlog, Sentry.
13. **Configuration** — pydantic-settings, .env, секреты.
14. **Backup** — автоматическое резервное копирование БД и файлов.

## 5. MVP vs V2

### Обязательно в MVP
- Стартовый экран (приветствие, описание, кнопка, ссылка на канал)
- Регистрация: ФИО, телефон, город
- Загрузка фото ВУ + OCR (Google/Yandex Vision) + структурная валидация под образец ВУ РК + сверка ФИО + проверка срока действия + проверка уникальности + эвристики редактирования (флаг для модератора)
- Загрузка видео-визитки
- Модерация через Telegram (админ-режим бота, без отдельной веб-панели)
- Уведомления: регистрация, следующий этап, отказ, повторная загрузка
- Базовый антиспам/rate-limit
- Логирование, бэкапы БД
- Docker-деплой на VPS (PS.KZ)

### Можно перенести в V2
- Полноценная веб-админ-панель (React/HTMX) с фильтрами и дашбордом
- Ролевая модель admin/moderator с логином и 2FA
- Специализированный SDK проверки подлинности документа (Smart Engines/Regula) — если после запуска фиксируется реальная проблема с поддельными документами, см. раздел 8
- Prometheus/Grafana, расширенный мониторинг
- Многоязычность
- Автоматизированная модерация видео-контента
- Голосование/рейтинг медийных участников (если потребуется публичная механика)
- Рассылки с сегментацией аудитории

## 6. Инфраструктура

### Вывод про Shared Hosting
**Shared hosting не подходит и не будет использован.** Причины:
- Telegram-бот требует постоянно работающий процесс (long polling) либо стабильный HTTPS-эндпоинт с полным контролем сертификата (webhook) — на классическом shared PHP-хостинге нет управления долгоживущими процессами.
- Нет SSH → невозможно установить Python-окружение, Redis, PostgreSQL, Docker, воркеры.
- Лимиты времени выполнения PHP-скрипта убьют синхронный OCR-запрос при пиковой нагрузке.
- Нет очередей/фоновых задач → OCR и обработка видео будут блокировать ответ пользователю → прямое нарушение требования «мгновенные ответы, отсутствие зависаний».
- Нет контроля над бэкапами, логами, мониторингом на нужном уровне.

**Вывод: нужен VPS.**

### Рекомендация VPS
Расчёт под 500–5000 участников: пиковая нагрузка — короткие всплески в начале акции и во время объявления новых активностей (регистрация + загрузка фото/видео), а не постоянный ровный трафик. Видео/фото сами по себе не обрабатываются CPU-интенсивно на стороне бота (кодирование/тяжёлая обработка не требуется — видео просто хранится, OCR уходит во внешний SDK/API), поэтому узкое место — количество одновременных соединений и работа воркеров, а не сырая вычислительная мощность.

- **CPU:** 2 vCPU для старта и всего диапазона до ~2000 участников; при приближении к верхней границе (5000) или явных пиках нагрузки — апгрейд до 4 vCPU (обычно без даунтайма, уточнить у PS.KZ порядок апгрейда)
- **RAM:** 4 GB старт — достаточно с учётом бюджетного OCR-подхода (без тяжёлого локального SDK-инференса, см. раздел 8), OCR-запросы уходят во внешний облачный API, а не считаются на VPS
- **Диск:** 80–100 GB NVMe SSD (видео — самый тяжёлый по объёму контент; при 5000 участников и видео ~20–50 МБ на человека это 100–250 GB суммарно за весь период акции — важно с самого начала выносить файлы в S3, а не держать на диске VPS, см. ниже)
- **ОС:** Ubuntu 24.04 LTS (доступна на PS.KZ VPS)
- **Регион/провайдер: PS.KZ, VPS-хостинг** — подтверждено заказчиком. У PS.KZ есть root/SSH-доступ, поддержка Docker Engine, ЦОД в Казахстане, что закрывает вопрос локализации ПДн по казахстанскому законодательству без дополнительных телодвижений. Точную стоимость тарифа под 2 vCPU/4 GB нужно свериться на [ps.kz/hosting/vps](https://www.ps.kz/hosting/vps) — базовые тарифы стартуют от ~3120 ₸/мес, но полная сетка с характеристиками не была доступна для проверки на момент написания плана.
- **Docker:** да, однозначно — docker-compose со стеком bot/worker/postgres/redis/caddy/(admin-panel в V2). Упрощает деплой, откат, воспроизводимость окружения.

| Статья | Стоимость |

| VPS PS.KZ, 2vCPU/4GB (сверить точный тариф на сайте) | ориентировочно ~15 000–25 000 ₸ (~$28–47) — **уточнить перед покупкой** |
| Домен | ~$10–15/год |

| **Итого MVP** | **≈ $35–60/мес** без учёта домена — на порядок дешевле варианта со специализированным SDK |

### Путь масштабирования
1. Вертикально: апгрейд VPS до 4 vCPU/8 GB при приближении к верхней границе диапазона (5000 участников) или явных признаках нагрузки (рост времени ответа, очередь в arq).
2. Вынос PostgreSQL на managed-БД (снижает риск потери данных, упрощает бэкапы) — оправдан уже на этом масштабе, т.к. потеря анкет/документов участников акции критична.
3. Горизонтально: несколько реплик бота/воркеров за общим Redis (aiogram/arq это поддерживают из коробки при stateless-дизайне) — актуально при пиках вокруг дедлайнов регистрации.
4. Файлы — в S3 с самого MVP, а не «переезд» (см. диск выше) — на этом масштабе объём видео делает локальное хранение на VPS узким местом почти сразу.
5. Если после запуска станет ясно, что через ручную модерацию проходит заметный поток поддельных документов — специализированный SDK (раздел 8) становится следующей статьёй бюджета, уже обоснованной реальными цифрами.

## 7. База данных

**PostgreSQL 16.**

Почему:
- ACID и unique-constraints — единственный надёжный способ гарантированно исключить повторную регистрацию (по telegram_id, нормализованному телефону, номеру документа) на уровне БД, а не только в коде.
- JSONB для хранения сырого ответа OCR-провайдера — гибкость без раздувания схемы, при этом остаётся возможность индексировать и запрашивать поля.
- Реляционная природа данных: пользователь → заявка → лог модерации → уведомления — естественно ложится на таблицы со связями, а не на документную модель.
- Зрелый инструментарий бэкапов (pg_dump/pg_basebackup), отличная async-поддержка через SQLAlchemy 2.0 + asyncpg.
- При росте нагрузки — PgBouncer для пулинга соединений, репликация для чтения.

## 8. OCR — распознавание водительского удостоверения

### Решение: бюджетная связка вместо специализированного SDK

Заказчик подтвердил: лицензия Smart Engines/Regula ($100–300+/мес) — слишком дорого для этого проекта. Реальная потребность заказчика (дословно): бот должен (1) распознать данные с ВУ, (2) сверить с базой — нет ли уже такой регистрации, (3) проверить, что удостоверение настоящее, (4) проверить, что срок не истёк. При этом заказчик готов прислать образец (эталон) бланка ВУ РК для настройки.

Это меняет архитектуру проверки подлинности: вместо покупки SDK, который сам «знает» все защитные элементы документа, — строим **собственную структурную валидацию под конкретный образец ВУ РК**, которую заказчик предоставит, плюс дешёвые эвристики, плюс человек-модератор как последний рубеж (он и так уже смотрит фото документа в очереди модерации перед одобрением). Это реалистичный компромисс: полная автоматическая детекция подделки (голограммы, микропечать, полиграфическая защита) — это ровно то, за что берут деньги специализированные SDK, и без бюджета на них такая проверка технически недостижима. План ниже даёт разумную защиту за счёт совпадения нескольких дешёвых сигналов, а не одного дорогого.

### Подход
1. **Извлечение текста** — Yandex Vision OCR (хорошо читает кириллицу, дёшево) с Google Cloud Vision как фолбэком, если Yandex недоступен или качество распознавания хуже ожидаемого.
2. **Структурная валидация под образец**: когда заказчик пришлёт эталонный бланк ВУ РК — строим парсер, который проверяет не только текст, но и что документ соответствует ожидаемому шаблону (набор обязательных полей на ожидаемых местах, формат номера ВУ РК, формат дат). Фото, не подходящее под структуру шаблона (не тот документ, обрезанное/нечитаемое фото, явно не бланк ВУ) — отклоняется автоматически с просьбой переснять, до похода к модератору.
3. **Эвристики на признаки редактирования** (дешёвые, не требуют платного SDK): проверка EXIF-метаданных файла (следы обработки в графическом редакторе), Error Level Analysis (ELA) на JPEG — стандартная открытая техника, подсвечивает области с несовпадающим уровнем сжатия (типичный след копипаста/замены текста на фото). Это не «доказательство подделки», а сигнал — при срабатывании заявка помечается `document_flagged` и уходит на приоритетную ручную проверку, а не авто-отклоняется.
4. **Сверка ФИО**: fuzzy-сравнение (rapidfuzz/Левенштейн) введённого пользователем ФИО и распознанного из документа — при несовпадении не авто-отказ, а флаг на ручную проверку.
5. **Проверка срока действия**: парсинг даты «действительно до» из распознанного текста, автоматическое отклонение при истёкшем сроке — это полностью автоматизируемая проверка, SDK для неё не нужен.
6. **Проверка уникальности**: номер ВУ — unique constraint в БД, блокирует повторную регистрацию даже с другого Telegram-аккаунта — тоже не требует SDK, чистая логика БД.
7. **Финальное решение по подлинности — за модератором**: карточка заявки в модерации (раздел 9) показывает фото документа, результат сверки ФИО и флаг эвристик редактирования одним экраном — человек принимает финальное решение «одобрить/отклонить», имея все автоматические сигналы перед глазами.

### Варианты OCR-провайдеров (текстовый слой)

| Провайдер | Плюсы | Цена (ориентировочно) |
|---|---|---|
| **Yandex Vision OCR** | Отличное качество на кириллице, простой REST API | ~150–300 ₸-эквивалент / 1000 запросов (биллинг в рублях, уточнить конвертацию/доступность оплаты из РК) |
| **Google Cloud Vision API** | Высокое качество, глобальная доступность, международный биллинг (проще оплатить из РК картой) | ~$1.5 / 1000 изображений |

**Рекомендация:** Google Cloud Vision как основной (проще с оплатой и доступностью из Казахстана), Yandex Vision как фолбэк/сравнение качества на кириллице во время пилота на реальных фото от заказчика.

### Путь эскалации, если бюджет позволит или мошенничество станет проблемой
Если после запуска окажется, что через ручную модерацию всё же проходит заметное число поддельных документов — это станет измеримым фактом (не догадкой), и тогда решение о покупке специализированного SDK будет обосновано конкретными цифрами, а не предположением на старте. Архитектурно OCR вынесен за интерфейс `services/ocr/base.py` — подключение Smart Engines/Regula в будущем не потребует переписывать остальную бизнес-логику (сверку ФИО, уникальность, модерацию).

## 9. Админ-панель

### MVP — Telegram-режим
- Администратор определяется списком Telegram ID в конфиге.
- Бот присылает администратору карточку следующей заявки в очереди: анкета (ФИО/телефон/город), фото ВУ, видео, результат OCR-сверки (совпадение/несовпадение ФИО подсвечено), срок действия документа, флаг сработавших эвристик редактирования фото (если есть) — модератор видит все автоматические сигналы на одном экране и принимает финальное решение по подлинности сам.
- Инлайн-кнопки: **Одобрить / Отклонить / Запросить повторную загрузку**.
- При отклонении — запрос причины (текстом или из готового списка).
- Все действия пишутся в `ModerationLog` (кто, когда, что, почему).

### V2 — Веб-панель
**Что видит администратор:**
- Дашборд: количество заявок по статусам (pending / approved / rejected / reupload_requested).
- Таблица заявок с колонками: ФИО, телефон, город, статус, дата подачи.
- Карточка заявки: полные данные, фото документа (zoom), видео-плеер, OCR-данные рядом с введёнными пользователем (с подсветкой расхождений).

**Фильтры:**
- По статусу заявки
- По городу
- По диапазону дат регистрации
- Поиск по ФИО/телефону
- По результату сверки ФИО (совпало/не совпало/требует внимания)

**Статусы заявки:**
- `draft` — анкета не завершена
- `pending_document` — ожидает фото ВУ
- `pending_ocr` — фото загружено, идёт распознавание
- `document_flagged` — расхождение ФИО/подозрение, нужна ручная проверка
- `pending_video` — ожидает видео-визитку
- `pending_moderation` — полный комплект, ожидает решения администратора
- `reupload_requested` — модератор запросил повторную загрузку
- `approved`
- `rejected`

**Действия администратора:**
- Одобрить / Отклонить (с причиной) / Запросить повторную загрузку (фото и/или видео отдельно)
- Просмотр истории действий по заявке
- Экспорт выборки в CSV/Excel
- Рассылка новости/активности сегменту пользователей (по статусу/городу)
- Управление ролями (super-admin создаёт modератор-аккаунты)

## 10. Безопасность

- **Защита от повторной регистрации:** unique-constraints в БД на telegram_id, нормализованный номер телефона (E.164) и номер документа; проверка на каждом шаге (при старте регистрации и повторно после OCR).
- **Защита от спама:** throttling-middleware на уровне aiogram (лимит сообщений/действий на пользователя в единицу времени, Redis-счётчики), cooldown после нескольких неудачных попыток OCR, простая проверка «не бот» на старте (нажатие кнопки).
- **Логирование:** структурированные JSON-логи (structlog), маскирование PII (телефон/номер документа частично скрываются в логах), request-id для трассировки цепочки событий, отдельные уровни для бота/воркеров/админки.
- **Резервное копирование:** ежедневный pg_dump с шифрованием, хранение вне VPS (второй регион/провайдер), ретенция 14–30 дней, регулярная проверка восстановления из бэкапа; версионирование/бэкап файлового хранилища (S3 versioning или отдельная копия).
- **Хранение файлов:** приватный S3-бакет (не public-read), доступ только через подписанные временные URL для админки, видео/фото не раздаются напрямую по постоянной ссылке.
- **Защита персональных данных:** явное согласие пользователя на обработку ПДн на этапе регистрации (с фиксацией времени согласия), шифрование чувствительных полей на уровне приложения/БД (номер документа, телефон), ограничение доступа к БД, HTTPS everywhere, соответствие Закону РК «О персональных данных и их защите» (см. раздел 6 — открытый вопрос локализации данных на территории РК), политика хранения/удаления данных по запросу пользователя.
- **Секреты:** .env не коммитится, в проде — переменные окружения/Docker secrets, ротация токенов бота при компрометации.
