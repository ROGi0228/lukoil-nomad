## 0. Резюме проекта

Telegram-бот для регистрации участников автопробега/путешествия (партнёр — Lukoil, есть медийные участники). Функции: приветствие → регистрация (ФИО/телефон/город) → загрузка фото водительского удостоверения с автоматическим OCR и сверкой → загрузка видео-визитки → модерация администратором → уведомления на всех этапах.

Ключевые нефункциональные требования: мгновенный отклик бота, отсутствие зависаний, работа 24/7, масштабируемость, защита персональных данных, защита от повторной регистрации и спама.

## 1. Архитектура и стек

### 1.1 Выбранный стек

| Слой | Технология | Причина |
|---|---|---|
| Язык | Python 3.12+ | Единый язык для бота, OCR и обработки изображений/видео — не нужно городить отдельный сервис на другом языке |
| Bot framework | **aiogram 3.x** | Нативный asyncio, встроенный FSM (важен для пошагового визарда регистрации), Router-архитектура (естественно ложится на SOLID/модульность), сильное middleware (throttling, логирование, DI сессии БД), большое активное RU-сообщество и документация |
| Web framework (admin API + webhook) | **FastAPI** | Async, автогенерация OpenAPI, легко переиспользовать Pydantic-схемы между ботом и админкой |
| ORM / миграции | SQLAlchemy 2.0 (async) + Alembic | Стандарт де-факто, полный контроль над схемой, безопасные миграции |
| База данных | **PostgreSQL 16** | ACID + уникальные constraints — критично для защиты от повторной регистрации; JSONB для сырых OCR-данных без раздувания схемы |
| Кэш / очередь / FSM-хранилище | **Redis 7** | Хранилище состояний aiogram FSM, брокер задач, счётчики антиспама/rate-limit |
| Фоновые задачи | **arq** (Redis-based async task queue) | OCR-запрос, обработка видео, рассылки — не блокируют event loop бота; легче Celery, полностью async, тот же Redis, что и FSM |
| Файловое хранилище | **S3-совместимое object storage** (MinIO на VPS или облачный S3) | Бот должен быть stateless (для будущего горизонтального масштабирования); диск VPS — не источник истины для медиафайлов |
| OCR | **Yandex Vision OCR / Google Cloud Vision** (текстовый слой) + собственный слой валидации (структура/формат/эвристики) | Специализированный SDK с проверкой подлинности (Smart Engines/Regula) признан слишком дорогим для бюджета проекта — заменён связкой «дешёвый OCR + структурная валидация под образец ВУ РК + финальная проверка модератором глазами». См. раздел 8 |
| Админ-панель | FastAPI + Jinja2/HTMX (без отдельной SPA-сборки) | Строится сразу как полноценная веб-панель (решение принято после Фазы 4, Telegram-режим как временный MVP отменён) — быстрее в разработке, чем React SPA, даёт полноценный интерфейс с фильтрами/таблицами. См. раздел 9 |
| Контейнеризация | Docker + docker-compose | Воспроизводимость, изоляция сервисов, простой rollback |
| Reverse proxy / TLS | Caddy | Автоматический HTTPS без ручной возни с certbot |
| Логирование | structlog → JSON логи (+ опционально Loki/Grafana в V2) | Структурированные логи, трассировка запросов, маскирование PII |
| Мониторинг ошибок | Sentry (бесплатный tier достаточно на старте) | Мгновенное обнаружение падений/зависаний — прямое требование к стабильности |
| CI/CD | GitHub Actions → сборка образа → деплой на VPS по SSH | Автоматизация без ручного деплоя |

### 1.2 Почему не альтернативы

- **PHP / shared hosting** — исключено (см. раздел 6): нет постоянного процесса, нет очередей, нет Redis/Postgres, лимиты времени выполнения ломают OCR-запросы.
- **python-telegram-bot / Telethon** — жизнеспособны, но FSM-эргономика aiogram 3 удобнее именно для мастера регистрации из нескольких шагов.
- **Node.js + Telegraf** — тоже валидный вариант, но пришлось бы либо выносить OCR/обработку изображений в отдельный Python-сервис, либо мириться с более слабой экосистемой CV/OCR в Node. Один язык — меньше точек отказа.
- **MongoDB** — данные принципиально реляционные (пользователь → заявка → лог модерации → уведомления), плюс нужны строгие unique-constraints — Postgres здесь естественнее и надёжнее.
- **Celery** вместо arq — тяжелее (требует отдельного брокера/конфигурации, много синхронного legacy-кода), для async-стека aiogram+FastAPI arq — более естественный выбор.

### 1.3 Плюсы / минусы стека

**Плюсы:** полностью async от бота до воркеров (OCR/видео не блокируют ответы пользователю); stateless-боты можно масштабировать горизонтально за Redis; дешёво в эксплуатации; зрелые, активно поддерживаемые библиотеки.

**Минусы:** требует VPS и базового Docker/DevOps-навыка (выше порог входа, чем shared hosting); Python GIL — CPU-тяжёлые операции (обработка изображений) обязаны идти через воркеры, а не в event loop бота (учтено архитектурой воркеров).

## 3. Модули системы

1. **Telegram Bot Core** — точка входа, роутинг, FSM.
2. **Registration** — сбор ФИО/телефон/город, валидация ввода.
3. **Document Verification (OCR)** — распознавание ВУ, сверка ФИО, проверка формата и уникальности.
4. **Video Intake** — приём видео-визитки, базовая валидация (размер/длительность/формат).
5. **Moderation** — очередь заявок, действия администратора, аудит-лог.
6. **Notifications** — все исходящие уведомления пользователю (статус, новости, активности).
7. **Database** — модели, репозитории, миграции.
8. **File Storage** — абстракция над S3/MinIO, подписанные URL.
9. **Admin Panel** — веб-панель (FastAPI + Jinja2/HTMX), строится сразу как основной вариант, без промежуточного Telegram-режима.
10. **Auth (Admin)** — логин/пароль для веб-панели, один общий admin-аккаунт в первой версии; роли admin/moderator + 2FA — доработка V2.
11. **Antifraud/Antispam** — rate-limiting, дедупликация, проверка уникальности документа.
12. **Logging & Monitoring** — structlog, Sentry.
13. **Configuration** — pydantic-settings, .env, секреты.
14. **Backup** — автоматическое резервное копирование БД и файлов.

2. `src/core/config.py`: `pydantic-settings` пытался JSON-распарсить `ADMIN_TELEGRAM_IDS` до того, как отрабатывал кастомный `field_validator`, и падал на строке вида `"123,456"` — добавлена аннотация `NoDecode`, чтобы разбор строки полностью остался за валидатором.
3. `src/workers/worker.py`: `arq` отказывается стартовать вообще без ни одной зарегистрированной задачи (`functions=[]` → `RuntimeError`) — добавлена временная задача-заглушка `health_check`, которая будет вытеснена реальными задачами в Фазе 3.

Вывод: планы на «живое тестирование» до Docker были не просто формальностью — все три бага были бы незаметны при чтении кода и всплыли только при реальном запуске.

Реализовано: `src/db/models/{user,application}.py` (+ `TimestampMixin` в `base.py`), `src/db/repositories/{user_repository,application_repository}.py`, `src/bot/states/registration_states.py`, `src/bot/keyboards/registration.py`, `src/bot/handlers/registration.py` (визард ФИО → телефон → город → согласие на ПДн → сохранение), `src/bot/utils/validators.py` + `tests/unit/test_validators.py` (20 тестов). `DbSessionMiddleware` дополнен коммитом/роллбэком по факту успеха хендлера (unit-of-work на апдейт), FSM переведён на `RedisStorage` (в Фазе 1 по умолчанию был `MemoryStorage`, что противоречило разделу 1 плана). Защита от повторной регистрации — на двух уровнях: `Application.phone`/`Application.user_id` unique-constraints в БД + прикладная проверка «уже есть анкета» перед стартом визарда.

**Тестирование:** полный цикл прогнан вживую в Docker (после генерации миграции через `alembic revision --autogenerate` против реального Postgres) — `/start` → «Принять участие» → ФИО → телефон → город → согласие → запись в БД, и повторный клик «Принять участие» корректно показывает статус вместо нового визарда. Также прогнаны `pytest` (20/20), `ruff` и `mypy --strict` в одноразовом контейнере `python:3.12-slim` (первый раз, когда mypy реально проверил файлы Фаз 0–1 — раньше это было невозможно из-за отсутствия рабочего Python 3.12 локально).

Живой прогон и линтеры вскрыли ещё 4 бага:
1. `pydantic-settings`/`NoDecode`-исправление из Фазы 1 работало корректно и здесь не потребовалось трогать.
2. `arq` в Фазе 1 уже был пофикшен `health_check`-заглушкой — без изменений.
3. **mypy strict** нашёл 6 проблем в файлах Фаз 0–1, не пойманных на синтаксической проверке: неиспользуемый `# type: ignore` в `config.py`, `no-any-return` в `logging.get_logger` (пофикшено через `cast`), отсутствующие типовые параметры у `dict`/`list` в `worker.py` (`dict[str, Any]`, `list[Any]`).
4. **SQLAlchemy `Enum(native_enum=False)` по умолчанию хранит `.name`, а не `.value`** — статус в БД сохранялся как `PENDING_DOCUMENT` вместо `pending_document`, расходясь с значениями `ApplicationStatus`, используемыми во всём остальном коде (сообщениях модератору, фильтрах и т.д.). Обнаружено прямым запросом к БД после первого живого теста. Исправлено `values_callable=lambda e: [m.value for m in e]` в `application.py`; миграция пересоздана автогенерацией после фикса, БД пересоздана и регистрация перепройдена — статус теперь `pending_document`.

**UX-доработки по запросу заказчика (после завершения фазы):**
- Убраны видимые пользователю пометки «[ПЛЕЙСХОЛДЕР]» из текста стартового экрана (`src/bot/handlers/start.py`) — заменены черновым, но связным текстом-заглушкой без служебных меток; финальный текст всё ещё ждёт бренд-материалы от заказчика (см. открытые вопросы).
- Шаг ввода телефона теперь предлагает кнопку «Отправить номер телефона» (`request_contact`) через `ReplyKeyboardMarkup` — номер подставляется автоматически из `message.contact`, ручной ввод остаётся рабочим fallback-путём. Добавлена проверка `contact.user_id == message.from_user.id`, чтобы нельзя было отправить чужой контакт вместо своего номера. Проверено вживую через Telegram (кнопка → номер сохранён в БД в нормализованном виде).

### Фаза 3 — Загрузка и проверка водительского удостоверения

**Образец документа:** заказчик прислал реальное фото бланка ВУ РК (обезличенный тестовый образец с именем «ЛЕЛЁТКА ИВАН ВЛАДИМИРОВИЧ»). Из него взята точная структура полей — номера 1–12 по международному образцу (Венская конвенция), которому следует бланк РК: 1 — фамилия, 2 — имя/отчество (кириллица/латиница через «/»), 3 — дата и место рождения, 4a/4b — даты выдачи/окончания, 4c — орган выдачи, 4d — ЖСН/IIN, 5 — номер ВУ (формат `AA NNNNNN`). Парсер (`services/ocr/parser.py`) и юнит-тесты построены под эту точную структуру, а не абстрактно.

**Полезная находка:** первые 6 цифр ИИН РК — дата рождения (YYMMDD), 7-й разряд кодирует век. Это даёт бесплатную перекрёстную проверку даты рождения (поле 3 бланка) против ИИН (поле 4d) без реализации контрольной суммы ИИН — алгоритм чек-суммы **сознательно не реализован**: без набора проверенных тестовых ИИН есть риск запрограммировать его неверно и начать отклонять настоящие документы (ложный отказ хуже отсутствия проверки). Реализовано и проверено на реальном образце: `861003399096` → `03.10.1986` — совпадает с бланком.

**Реализовано:**

- `src/services/storage/{base,s3_storage}.py` — обёртка над aioboto3/MinIO

**Тестирование:** живой прогон в Docker плюс 51 юнит-тест (`pytest`), `ruff`/`mypy --strict` чистые.

**Живой прогон нашёл 4 реальных бага** (не осознавались бы без прогона в Docker):
1. `GoogleVisionOCR()` создавался **вне** `try/except` в `ocr_tasks.py` — при недоступном OCR (нет креденциалов, сеть, квота) весь arq-таск падал необработанным исключением вместо аккуратного fallback-сообщения пользователю. Конструктор перенесён внутрь `try`.
2. `arq` синхронно вызывает `asyncio.get_event_loop()` при создании `Worker`, до старта цикла событий — под `uvloop` (транзитивная зависимость `arq` на Linux, ранее не активировалась, пока `worker.py` не начал импортировать `aiogram`) это падает с `RuntimeError: There is no current event loop`. Фикс — явный `asyncio.set_event_loop(asyncio.new_event_loop())` в начале `worker.py` до того, как `arq` создаёт `Worker`.
3. После сброса FSM-состояния в `document.py` (сразу после постановки задачи в очередь) неудача OCR в отдельном процессе воркера оставляла пользователя без активного состояния — повторно присланное фото никем не обрабатывалось («update is not handled» в логах). Добавлен `_reset_fsm_to_waiting_photo` в `ocr_tasks.py`, который через `RedisStorage`/`StorageKey` напрямую возвращает FSM-состояние `DocumentStates.waiting_photo` из воркера.
4. **Race condition**: `arq_pool.enqueue_job(...)` вызывался в `document.py` до фактического коммита транзакции (коммит происходит позже, в `DbSessionMiddleware`, после возврата хендлера) — воркер в отдельном процессе иногда успевал обработать задачу и закоммитить свой результат (откат статуса на `pending_document`) быстрее, чем коммитился сам апдейт бота, и более поздний коммит бота (`status=pending_ocr`) молча затирал результат воркера — статус необратимо зависал на `pending_ocr`. Найдено прямым запросом к БД после теста (в логах ошибок не было — таск отработал «успешно»). Исправлено: `db_session.commit()` вызывается в хендлере явно, до постановки задачи в очередь, а не `flush()`.

**Живой вызов Google Vision API (обновление после получения реального service account):**
Заказчик завёл проект в Google Cloud, включил Cloud Vision API, создал service account с ролью Editor и сгенерировал JSON-ключ. Ключ смонтирован в контейнер `worker` через `docker-compose.override.yml` (гитигнорится — путь на конкретной машине не должен попасть в репозиторий; на VPS понадобится свой override-файл с путём к ключу на сервере) и `.env`-переменную `GOOGLE_APPLICATION_CREDENTIALS=/run/secrets/google_vision_credentials.json`.

Прогнаны оба сценария на реальном фото присланного образца ВУ:
- **С намеренным несовпадением ФИО** (анкета оформлена на другое имя, чем на документе): `document_number="AF 977776"`, `document_iin="861003399096"`, `document_expiry_date=2027-04-11` — все поля распознаны верно, `verification_flags=["fio_mismatch"]`, статус `document_flagged` — антифрод-проверка сработала корректно.
- **С совпадающим ФИО** («Лелётка Иван Владимирович», как на бланке): те же поля, `verification_flags=[]`, статус `pending_video` — чистый проход без единого флага.

Реальный ответ Google Vision (document_text_detection) оказался структурно очень близким к тексту, смоделированному вручную для юнит-тестов (с мелкими OCR-искажениями вроде «4с)» кириллицей вместо латиницы и «жKCH/IIN» вместо «ЖСН/IIN») — парсер и валидаторы, написанные и протестированные ДО получения реального ключа, отработали на настоящем ответе без единой правки. OCR-часть пайплайна теперь полностью подтверждена вживую, ни одного открытого вопроса по Фазе 3 не осталось.

**Изменение поведения при несовпадении ФИО (по решению заказчика, после демонстрации живого прогона):**
Изначально `fio_mismatch` обрабатывался как обычный флаг — статус `document_flagged`, сообщение «нужна ручная проверка модератором» (см. пример прогона выше). Заказчик решил, что это неверно: несовпадение ФИО — не пограничный случай вроде смазанного скана, а однозначный сигнал «в боте фото чужого документа», и ждать модератора для этого незачем. Теперь при `fio_mismatch`:
- пользователю сразу пишется прямым текстом «это не ваши права» с просьбой прислать своё удостоверение;
- статус возвращается на `pending_document`, FSM переводится обратно в `DocumentStates.waiting_photo` (тот же механизм, что и при технической ошибке OCR) — пользователь может сразу прислать корректное фото, не дожидаясь модератора;
- `document_photo_key`/`document_number`/`document_iin`/`document_expiry_date` очищаются от этой заявки — **важно**: если оставить чужой номер/ИИН привязанным к этой заявке, при последующей регистрации настоящего владельца документа проверка на дубликат ложно заблокирует именно его, а не мошенника. `verification_flags=["fio_mismatch"]` остаётся для истории/аудита.
- остальные флаги (истёкший срок, нераспознанные поля, эвристики редактирования, дубликат) по-прежнему уходят на ручную проверку модератором без изменений.

Явное обсуждение того, что автоматика **не проверяет подлинность физического носителя** (распечатка на A4 вместо пластиковой карты пройдёт все текущие проверки, если данные оформлены в правильном формате) — см. пункт «Известные ограничения» ниже. Решение осталось прежним: не покупать специализированный SDK, полагаться на визуальный осмотр модератором как финальный рубеж (Фаза 5).

**Известные ограничения бюджетной OCR-связки (зафиксировано явно, чтобы не забыть):**
Ни один из текущих чеков не проверяет физический носитель документа — OCR, `document_validator`, `fio_matcher` и проверка дубликата работают только с текстом, который вернул Google Vision, а EXIF/ELA ловят следы цифрового редактирования файла, а не признаки того, что сфотографирован лист бумаги, а не пластиковая карта. Аккуратно распечатанные и заламинированные данные с правильным ФИО/форматом номера и ИИН пройдут все автоматические проверки. Это ожидаемое следствие решения не покупать специализированный SDK (Smart Engines/Regula) — единственный реальный барьер против такой подделки в текущей архитектуре — визуальный осмотр фото модератором (Фаза 5), которой пока не существует. Обсуждали с заказчиком: можно добавить дешёвую эвристику «похоже ли на фото пластиковой карты» (по пропорциям, скруглённым углам, бликам от ламинации) — отложено на потом, отсеет только самые примитивные попытки, не защитит от тщательной подделки.

Живой прогон нашёл 2 бага:
1. **Реальный, в коде**: `dashboard.py` (только модерация Application) никогда не импортирует `src.db.models.user` — а `Application.user` объявлен как `Mapped[User]` со строковой аннотацией (`from __future__ import annotations`). SQLAlchemy резолвит такие relationship-аннотации по имени класса в общем реестре маппера при первом реальном запросе, а не при объявлении модели — и без импорта `User` где-либо в процессе admin-panel конфигурация мапперов падала с `InvalidRequestError: ... failed to locate a name ('User')`. В процессе бота эта проблема не проявлялась случайно: `registration.py` всегда импортирует и `user_repository`, и `application_repository` вместе. Исправлено централизованно: `src/db/models/__init__.py` теперь импортирует все модели — импорт любого подмодуля пакета гарантированно регистрирует все классы перед первым запросом, независимо от точки входа (бот/воркер/admin-panel).
2. **Мой собственный, в тестовых данных, не в коде**: первая попытка засеять тестовые кириллические записи через `Get-Content | docker compose exec -T postgres psql` в PowerShell побила кодировку (кириллица превратилась в `?????`) — из-за этого фильтры по городу/ФИО не находили ничего, что выглядело как баг в коде фильтрации. Пересеял через Bash-heredoc напрямую в `docker compose exec -T`, кодировка сохранилась корректно, после чего все фильтры дали ожидаемые числа.

Реализовано за один проход (5.3+5.4 естественно легли вместе): `services/storage/s3_storage.py` — `presigned_url()` через отдельный «публичный» S3-клиент (`S3_PUBLIC_ENDPOINT_URL`) — SigV4 подписывает Host как часть запроса, поэтому подписанную ссылку для браузера нельзя генерировать тем же клиентом, что обращается к MinIO по внутреннему docker-имени `minio`. `src/bot/{fsm_control,notify}.py` — вынесены из `ocr_tasks.py` (были там как приватные `_set_fsm_state`/`_notify_user`) в общие модули, чтобы админ-панель могла использовать тот же механизм возврата FSM-состояния и отправки уведомлений, не дублируя код и не импортируя из `workers`. `db/repositories/moderation_log_repository.py`, `application_repository.get_application`. `admin_panel/routers/applications.py` — детальный экран + 4 POST-действия, `Bot` теперь живёт в `app.state` через FastAPI `lifespan` (не создаётся заново на каждый клик). `display.py` дополнен `FLAG_LABELS`/`ACTION_LABELS`.

**Тестирование:** живой прогон в Docker — все 4 действия модератора прогнаны через curl на реальной заявке (id=8, из Фазы 4): `request-photo` → статус и поля корректно сброшены; `request-video` → аналогично; `reject` с причиной; `approve`. Presigned URL на фото проверен отдельным curl-запросом — отдаёт реальный JPEG (104 КБ, тот же файл, что заливали в Фазе 3). Каждое действие подтверждено и в БД (`applications`/`moderation_logs`), и в реальных сообщениях Telegram-бота.

**Расследование (не баг, но стоит записи):** тестируя `reject` с кириллической причиной через `curl` в этом Windows-окружении, несколько раз подряд получил на выходе битую кодировку — сначала решил, что нашёл четвёртый баг за сессию. Разобрался: (1) `curl -d "reason=Кириллица"` — Windows-сборка curl.exe кодирует нелатинские символы аргумента командной строки в системную кодовую страницу, а не UTF-8, до того как percent-encode; (2) `--data-binary` с файлом в UTF-8 без percent-encoding — тоже неверно, `application/x-www-form-urlencoded` requires percent-encoded non-ASCII, сырые UTF-8-байты в теле — невалидный формат сам по себе. Правильный вариант — `curl --data-urlencode "reason@file.txt"` (кодирует содержимое файла корректно как UTF-8 и не идёт через argv). С ним причина сохранилась и дошла до Telegram идеально: «Проверка кодировки причины отказа». Итог: сам код (FastAPI `Form`, SQLAlchemy, asyncpg, Postgres) с самого начала обрабатывал кириллицу верно — все несоответствия были в моих способах тестирования через Windows-инструменты, не в продакшен-коде.

#### 5.5 — Базовая защита панели
```
☑ CSRF-защита форм
☑ Rate-limit на попытки логина (Redis-counters, тот же паттерн, что и throttling бота)
```

Реализовано: `src/admin_panel/csrf.py` — токен генерируется через `secrets.token_urlsafe(32)`, хранится в сессии, встраивается скрытым полем во все формы (`login.html`, `dashboard.html`, `application_detail.html`), проверяется FastAPI-зависимостью `csrf_protect` через `secrets.compare_digest` (не самописное собственное сравнение строк — защита от timing-атак). `src/admin_panel/rate_limit.py` — `register_login_attempt`, тот же паттерн Redis `INCR`+`EXPIRE`, что и throttling-middleware бота: 5 попыток / 300 секунд, ключ — IP клиента (не сессия/кука — переживает сброс кук). `main.py` lifespan теперь создаёт и закрывает ещё и `Redis`-клиент (`app.state.redis`), не только `Bot`. `csrf_protect` подключена ко всем POST-роутам (`login`, `logout`, 4 действия модератора).

**Тестирование:** `tests/unit/test_csrf.py` (4 теста: отсутствие токена → 422, неверный токен → 403, совпадающий токен → 200, токен из чужой сессии → 403) — все через `TestClient`+`SessionMiddleware`. `ruff`/`mypy --strict`/`pytest` — 70/70 чистые. Живой прогон в Docker: curl подтвердил все три ветки CSRF (422/403/303), rate-limit подтверждён 7 быстрыми попытками логина (401×4, затем 429×3) и напрямую сверен с ключом в Redis (`admin_login_attempts:<ip>`, TTL корректный). Затем то же самое подтверждено пользователем вживую в браузере: залогинился, открыл карточку заявки, прогнал все 4 действия модератора (approve/reject/request-photo/request-video) — все 4 уведомления дошли в Telegram корректно, значит формы с CSRF-токеном не мешают легитимным запросам.

Живой прогон нашёл 1 баг (визуальный, не функциональный): кнопки «Запросить фото заново» / «Запросить видео заново» отображались пустыми белыми прямоугольниками без видимого текста. Причина: `:root` объявлял `color-scheme: light dark`, но переменные темы (`--bg`, `--surface`, `--text` и т.д.) имели только светлые значения — тёмного набора не было вообще. Базовый класс `.action-button` не задавал `color` явно (в отличие от `--approve`/`--reject`, где `color: #fff` шёл вместе с цветным фоном) — при тёмной теме браузера/ОС к кнопке применялся дефолтный светлый цвет текста браузера поверх светлого фона `var(--surface)`, из-за чего текст становился невидимым. Заодно с исправлением сделан полный редизайн панели (по просьбе пользователя): `src/admin_panel/static/style.css` — добавлен полноценный набор тёмной темы через `@media (prefers-color-scheme: dark)`, все интерактивные элементы получили явный `color`, добавлены цветные статус-бейджи (жёлтый/оранжевый/зелёный/красный в зависимости от статуса — `src/admin_panel/display.py: STATUS_CSS_CLASS`/`status_css_class()`, используется в `dashboard.py`/`applications.py`), кнопки разделены по иерархии (`--approve` зелёная, `--reject` красная, `--secondary` — нейтральная серо-синяя для «запросить заново»), добавлены тени/скругления/hover-состояния, таблица заявок обёрнута в горизонтально скроллящийся контейнер для узких экранов. Пользователь подтвердил в браузере: «общий вид теперь лучше».

Новое, сделано в рамках финального чек-листа: на сервере `/root/backups/backup.sh` (cron `0 22 * * *`, то есть 03:00 по Алматы) — `pg_dump` через `docker compose exec postgres` (переменные из `.env`, `set -a; source .env`) + `tar` дампа docker-тома `nomad-lukoil_minio-data` (фото/видео), оба гзипованы, ретеншн 14 дней (`find -mtime +14 -delete`), лог каждого прогона в `backup.log`. Прогнан вручную один раз для проверки — оба файла создались, `pg_dump` открыт и проверен (валидный SQL-дамп), затем встроен в crontab. **Важная оговорка:** бэкап лежит на том же диске VPS, это НЕ offsite — если весь сервер пропадёт (не просто испортится БД, а исчезнет сама виртуалка), бэкапы пропадут вместе с ним. Для истинного offsite нужно периодически скачивать `/root/backups/*` на свою машину через `pscp` — сделали это осознанно как компромисс без завязки на ещё один облачный аккаунт; если понадобится совсем надёжно — можно позже.

Sentry — сознательно отложен по решению заказчика (не критично на этом масштабе, structlog + маскирование PII уже дают наблюдаемость по логам; можно подключить позже одной переменной `SENTRY_DSN`, которая уже читается конфигом).

Заказчик прислал 5 требований одним сообщением — прежде чем писать код, уточнил три архитектурно значимых момента (см. переписку): (1) Instagram нельзя проверить программно — Telegram-боты не имеют доступа к Instagram API для проверки подписки конкретного пользователя, решили делать честное слово с кнопкой; (2) для реальной проверки Telegram-канала и автопостинга видео бот должен быть админом канала — подтверждено, уже добавлен; (3) казахские переводы — не носитель языка, делаю черновой машинный перевод сейчас, заказчик вычитает и поправит после того, как увидит вживую (не блокирует запуск).

**Архитектура:** `src/bot/i18n.py` — центральный каталог текстов `{key: {"ru": ..., "kk": ...}}` + функции `t(lang, key, **kwargs)`/`resolve_lang(value)`. Все хендлеры (`start.py`, `registration.py`, `document.py`, `video.py`), воркер (`ocr_tasks.py`) и админ-панель (`applications.py`) переведены с хардкода строк на `t(lang, ...)`. Язык пользователя читается из `User.language` (БД) везде, где уже есть загруженный `User` — единственное исключение: сама регистрационная анкета (`registration.py`, шаги ФИО/телефон/город) хранит `lang` в FSM-данных состояния (`state.update_data`), это безопасно, так как эти шаги идут без прерываний из другого процесса. Для `document.py`/`video.py`/воркера/админ-панели, где переходы между состояниями могут прийти извне (воркер, модератор), язык каждый раз берётся из БД — надёжнее, чем полагаться на сохранность FSM-данных через `set_fsm_state`.

Проверка подписки — `src/bot/utils/subscription.py: is_subscribed_to_channel()`, использует `bot.get_chat_member(chat_id=REQUIRED_CHANNEL_USERNAME, user_id=...)`, статусы `creator/administrator/member/restricted` считаются подпиской. Пустой `REQUIRED_CHANNEL_USERNAME` отключает проверку целиком (для локальной разработки без настоящего канала). Гейт стоит один раз — перед первым входом в регистрацию (по кнопке «Принять участие»), не перепроверяется на каждом шаге.

Номер участника — `application_repository.next_participant_number()`: подсчёт уже присвоенных номеров + 1, без отдельной SQL-последовательности (при масштабе ~100 участников и одобрении по одному через админ-панель гонки практически исключены). Автопостинг — `applications.py: _announce_in_channel()`, скачивает видео из S3 и отправляет в канал через `bot.send_video` с подписью `channel_announcement`; ошибка автопостинга (например, видео не докачалось) логируется и не блокирует само одобрение заявки — заявка в любом случае помечается одобренной, участник в любом случае получает уведомление.

Миграция `c2c43329bb2b` — `users.language` (nullable String(2)), `applications.participant_number` (nullable unique String(20)).

**Тестирование:** `ruff`/`mypy --strict`/`pytest` (71/71) чистые локально перед деплоем, задеплоено, живой прогон через реального бота подтверждён заказчиком.

**Живые правки после первого деплоя (в рамках этой же фазы, по факту тестирования заказчиком):** двуязычный экран дублировал текст с полным welcome — сделан короче и отдельно от welcome; полный ребрендинг текстов бота на «LUKOIL NOMAD» по финальному сценарию заказчика (i18n переписан целиком, казахский — черновой машинный перевод); добавлены кнопка «Ввести данные заново» на экране согласия, ветка «У меня нет прав»/«У меня есть права» на экране запроса документа, объединение ошибок валидации видео в одно сообщение; казахские буквы (Әә Ғғ Ққ Ңң Өө Ұұ Үү Һһ Іі) добавлены в валидацию ФИО/города — раньше отклоняли настоящие казахские имена; найдены и исправлены две реальные OCR-путаницы кириллица/латиница (омоглифы) — в ФИО (фамилия «СТАРОВ» иногда читалась как «CTAPOB» латиницей) и в номере ВУ (серия «BB» иногда читалась как кириллическая «ВВ») — оба места нормализуют одну сторону перед сравнением; меню команд Telegram (`/start`, `/status`, `/language`, `/admin` только у админов); время в админ-панели переведено в Asia/Almaty; новое действие `approve-document` для заявок с флагом `DOCUMENT_FLAGGED`, у которых ещё не было видео (раньше моdератору было нечем нажать — «Одобрить» открывало заявку без видео, «Запросить видео заново» звучало неверно для того, кто ещё ни разу не отправлял); переключатель «Закрыть/открыть приём заявок» в админ-панели с рассылкой не дошедшим до модерации; исправлен баг с «сырыми» HTML-тегами в уведомлениях из admin-panel/воркера (у них не был выставлен `parse_mode=HTML` на объекте `Bot`, в отличие от основного процесса бота).

### Фаза 11 — Отбор участников и голосование
```
☑ Модель: стадия отбора на Application (пройден этап 1 / не прошёл / финалист-победитель)
☑ Отметка блогера на заявке (Application.is_blogger) — для будущего добавления в команду (Фаза 12)
☑ Тексты: прошёл в голосование / не прошёл этап 1 / победитель / не прошёл финал
☑ Админ-панель: страница «Отбор» — выбор прошедших этап 1 из одобренных, рассылка обеих групп
☑ Админ-панель: тот же экран для финального отбора победителей из прошедших в голосование
```

Голосование как таковое — вручную по реакциям/комментариям под постами в канале (уже публикуются автопостом при одобрении, Фаза 10), никакого автоматического подсчёта голосов не строим — заказчик сам решает, кто прошёл, через попап в админке с чекбоксами. Двухэтапный отбор: одобренные (Фаза 5) → выбор прошедших в голосование (этап 1, с рассылкой обеим группам) → выбор финальных победителей из прошедших в голосование (этап 2). Победители дальше идут в команды (Фаза 12).

**Реализовано:** `SelectionStage` enum (`src/shared/enums.py`) — независим от `ApplicationStatus`, живёт поверх уже одобренных заявок. `src/admin_panel/routers/selection.py` — страница `/selection` с двумя таблицами-попапами (чекбоксы + одна кнопка submit на каждую), `/selection/stage1` и `/selection/stage2` обрабатывают выбор: отмеченные получают одно уведомление, оставшиеся — другое. `application_repository.list_stage1_candidates`/`list_stage2_candidates` — простые выборки по `status=APPROVED and selection_stage IS NULL` / `selection_stage=VOTING`. Отметка блогера — `POST /applications/{id}/toggle-blogger`, простое переключение флага без уведомлений и без влияния на FSM. Бейджи стадии отбора и блогера добавлены на карточку заявки.

**Тестирование:** `ruff`/`mypy --strict`/`pytest` (75/75) чистые. Живой прогон локально: 3 тестовые одобренные заявки → отправил 2 в голосование, 1 отклонил на этапе 1 → проверил в БД правильные `selection_stage`; из прошедших в голосование выбрал финального победителя → проверил, что второй получил `eliminated_stage2`, а не участвовавший в голосовании (`eliminated_stage1`) не попал в список кандидатов этапа 2 — фильтрация по стадиям работает верно. ### Фаза 12 — Команды, задания, баллы
```
☑ Модели: Team (до 3 участников + опционально блогер), Task (гибкое расписание), TaskDispatch (доставка+выполнение по командам)
☑ Админ-панель: подвкладка «Команды» — создание команды, добавление победителей и блогеров
☑ Админ-панель: подвкладка «Задания» — дата/время отправки, дедлайн (опционально), флаг «задание дня», штраф за просрочку
☑ Задания-триггеры — отправка команде через N часов/минут после того, как ЭТА ЖЕ команда выполнит другое задание
☑ Фоновый планировщик (arq cron) — рассылка заданий по расписанию и по триггеру, проверка дедлайнов, начисление штрафов
☑ Бот: кнопка «Выполнено» в задании — первый нажавший из команды засчитывает выполнение всей команде
☑ Начисление баллов по месту завершения (1-е место — 5 баллов, 2-е — 3, 3-е — 1) — одинаково для любого задания, с дедлайном или без, штраф за просрочку
☑ Рейтинг команд в админ-панели
```

Механика подтверждена заказчиком: любой участник команды может нажать «Выполнено» — не привязано к капитану. Блогер добавляется в команду и получает задания через бота так же, как обычные участники — он проходит обычную регистрацию (ФИО/телефон/город, может не доходить до отправки прав), после чего заказчик вручную помечает его как блогера в админ-панели.

**Реализовано:** модели `Team`/`Task`/`TaskDispatch` (`src/db/models/`) + `Application.team_id` FK — членство в команде хранится только на заявке, отдельной таблицы связей нет, так как участник/блогер состоит максимум в одной команде. `TaskDispatch` — одна строка на пару (задание, команда) с уникальным ограничением, хранит `sent_at`/`completed_at`/`completed_by_user_id`/`points_awarded`/`penalty_applied`. У `Task` поле `deadline_at` — nullable сквозь всю цепочку (модель/миграция/cron-проверка штрафа/бот/шаблоны): «Без дедлайна» в админке — штраф никогда не начисляется. Баллы: `points_for_completion_rank()` в `task_repository.py` — 5/3/1 за первые три места, 0 дальше; ранг считается в реальном времени по числу уже завершённых на момент нажатия «Выполнено» диспетчей, независимо от наличия дедлайна или типа задания — единственная проверка перед начислением: не наступил ли уже штраф/не выполнено ли уже, и (если дедлайн есть) не истёк ли он. Расписание — два режима: фиксированное время (`send_at`, как раньше) или «после другого задания» — `Task.trigger_task_id` + `Task.trigger_delay_minutes`, при этом `send_at` для таких заданий NULL. Планировщик — три arq cron-джоба в `src/workers/tasks/task_scheduler.py`: `dispatch_due_tasks` (фиксированное время, всем командам разом), `dispatch_trigger_based_tasks` (для каждого задания-триггера проверяет завершённые диспетчи задания-источника по командам и, когда пройдёт `trigger_delay_minutes` после завершения, создаёт диспетч именно для этой команды — идемпотентность через уникальность (task_id, team_id), не через общий флаг), `apply_deadline_penalties`. Бот: `src/bot/handlers/tasks.py` — любое нажатие «Выполнено» первым из команды засчитывает выполнение всей команде. Админ-панель: `/teams` и `/tasks` (переключатель «В заданное время» / «После другого задания» через CSS `:has()`, без JS; таблица заданий показывает «После «X» +Yч Zм» и «N / M команд» для заданий-триггеров вместо единого «Разослано: Да/Ожидает»).

**Тестирование:** `ruff`/`mypy --strict`/`pytest` (75/75) чистые. Живой прогон локально (без запуска `bot`): для заданий без дедлайна и «заданий дня» напрямую воспроизвёл логику начисления баллов на реальных диспетчах — получил те же 5/3/1 очка, что и для заданий с дедлайном, никакой разницы в поведении. ## 6. Инфраструктура

### Вывод про Shared Hosting
**Shared hosting не подходит и не будет использован.** Причины:
- Telegram-бот требует постоянно работающий процесс (long polling) либо стабильный HTTPS-эндпоинт с полным контролем сертификата (webhook) — на классическом shared PHP-хостинге нет управления долгоживущими процессами.
- Нет SSH → невозможно установить Python-окружение, Redis, PostgreSQL, Docker, воркеры.
- Лимиты времени выполнения PHP-скрипта убьют синхронный OCR-запрос при пиковой нагрузке.
- Нет очередей/фоновых задач → OCR и обработка видео будут блокировать ответ пользователю → прямое нарушение требования «мгновенные ответы, отсутствие зависаний».
- Нет контроля над бэкапами, логами, мониторингом на нужном уровне.

**Вывод: нужен VPS.**

### Рекомендация VPS
Расчёт под 500–5000 участников: пиковая нагрузка — короткие всплески в начале акции и во время объявления новых активностей (регистрация + загрузка фото/видео), а не постоянный ровный трафик. Видео/фото сами по себе не обрабатываются CPU-интенсивно на стороне бота (кодирование/тяжёлая обработка не требуется — видео просто хранится, OCR уходит во внешний SDK/API), поэтому узкое место — количество одновременных соединений и работа воркеров, а не сырая вычислительная мощность.

- **CPU:** 2 vCPU для старта и всего диапазона до ~2000 участников; при приближении к верхней границе (5000) или явных пиках нагрузки — апгрейд до 4 vCPU (обычно без даунтайма, уточнить у PS.KZ порядок апгрейда)
- **RAM:** 4 GB старт — достаточно с учётом бюджетного OCR-подхода (без тяжёлого локального SDK-инференса, см. раздел 8), OCR-запросы уходят во внешний облачный API, а не считаются на VPS
- **Диск:** 80–100 GB NVMe SSD (видео — самый тяжёлый по объёму контент; при 5000 участников и видео ~20–50 МБ на человека это 100–250 GB суммарно за весь период акции — важно с самого начала выносить файлы в S3, а не держать на диске VPS, см. ниже)
- **ОС:** Ubuntu 24.04 LTS (доступна на PS.KZ VPS)
- **Регион/провайдер: PS.KZ, VPS-хостинг** — подтверждено заказчиком. У PS.KZ есть root/SSH-доступ, поддержка Docker Engine, ЦОД в Казахстане, что закрывает вопрос локализации ПДн по казахстанскому законодательству без дополнительных телодвижений. Точную стоимость тарифа под 2 vCPU/4 GB нужно свериться на [ps.kz/hosting/vps](https://www.ps.kz/hosting/vps) — базовые тарифы стартуют от ~3120 ₸/мес, но полная сетка с характеристиками не была доступна для проверки на момент написания плана.
- **Docker:** да, однозначно — docker-compose со стеком bot/worker/postgres/redis/caddy/admin-panel. Упрощает деплой, откат, воспроизводимость окружения.

### Путь масштабирования
1. Вертикально: апгрейд VPS до 4 vCPU/8 GB при приближении к верхней границе диапазона (5000 участников) или явных признаках нагрузки (рост времени ответа, очередь в arq).
2. Вынос PostgreSQL на managed-БД (снижает риск потери данных, упрощает бэкапы) — оправдан уже на этом масштабе, т.к. потеря анкет/документов участников акции критична.
3. Горизонтально: несколько реплик бота/воркеров за общим Redis (aiogram/arq это поддерживают из коробки при stateless-дизайне) — актуально при пиках вокруг дедлайнов регистрации.
4. Файлы — в S3 с самого MVP, а не «переезд» (см. диск выше) — на этом масштабе объём видео делает локальное хранение на VPS узким местом почти сразу.
5. Если после запуска станет ясно, что через ручную модерацию проходит заметный поток поддельных документов — специализированный SDK (раздел 8) становится следующей статьёй бюджета, уже обоснованной реальными цифрами.

## 7. База данных

**PostgreSQL 16.**

Почему:
- ACID и unique-constraints — единственный надёжный способ гарантированно исключить повторную регистрацию (по telegram_id, нормализованному телефону, номеру документа) на уровне БД, а не только в коде.
- JSONB для хранения сырого ответа OCR-провайдера — гибкость без раздувания схемы, при этом остаётся возможность индексировать и запрашивать поля.
- Реляционная природа данных: пользователь → заявка → лог модерации → уведомления — естественно ложится на таблицы со связями, а не на документную модель.
- Зрелый инструментарий бэкапов (pg_dump/pg_basebackup), отличная async-поддержка через SQLAlchemy 2.0 + asyncpg.
- При росте нагрузки — PgBouncer для пулинга соединений, репликация для чтения.

## 8. OCR — распознавание водительского удостоверения

### Решение: бюджетная связка вместо специализированного SDK

Заказчик подтвердил: лицензия Smart Engines/Regula ($100–300+/мес) — слишком дорого для этого проекта. Реальная потребность заказчика (дословно): бот должен (1) распознать данные с ВУ, (2) сверить с базой — нет ли уже такой регистрации, (3) проверить, что удостоверение настоящее, (4) проверить, что срок не истёк. При этом заказчик готов прислать образец (эталон) бланка ВУ РК для настройки.

Это меняет архитектуру проверки подлинности: вместо покупки SDK, который сам «знает» все защитные элементы документа, — строим **собственную структурную валидацию под конкретный образец ВУ РК**, которую заказчик предоставит, плюс дешёвые эвристики, плюс человек-модератор как последний рубеж (он и так уже смотрит фото документа в очереди модерации перед одобрением). Это реалистичный компромисс: полная автоматическая детекция подделки (голограммы, микропечать, полиграфическая защита) — это ровно то, за что берут деньги специализированные SDK, и без бюджета на них такая проверка технически недостижима. План ниже даёт разумную защиту за счёт совпадения нескольких дешёвых сигналов, а не одного дорогого.

### Подход
1. **Извлечение текста** — Yandex Vision OCR (хорошо читает кириллицу, дёшево) с Google Cloud Vision как фолбэком, если Yandex недоступен или качество распознавания хуже ожидаемого.
2. **Структурная валидация под образец**: когда заказчик пришлёт эталонный бланк ВУ РК — строим парсер, который проверяет не только текст, но и что документ соответствует ожидаемому шаблону (набор обязательных полей на ожидаемых местах, формат номера ВУ РК, формат дат). Фото, не подходящее под структуру шаблона (не тот документ, обрезанное/нечитаемое фото, явно не бланк ВУ) — отклоняется автоматически с просьбой переснять, до похода к модератору.
3. **Эвристики на признаки редактирования** (дешёвые, не требуют платного SDK): проверка EXIF-метаданных файла (следы обработки в графическом редакторе), Error Level Analysis (ELA) на JPEG — стандартная открытая техника, подсвечивает области с несовпадающим уровнем сжатия (типичный след копипаста/замены текста на фото). Это не «доказательство подделки», а сигнал — при срабатывании заявка помечается `document_flagged` и уходит на приоритетную ручную проверку, а не авто-отклоняется.
4. **Сверка ФИО**: fuzzy-сравнение (rapidfuzz/Левенштейн) введённого пользователем ФИО и распознанного из документа — при несовпадении не авто-отказ, а флаг на ручную проверку.
5. **Проверка срока действия**: парсинг даты «действительно до» из распознанного текста, автоматическое отклонение при истёкшем сроке — это полностью автоматизируемая проверка, SDK для неё не нужен.
6. **Проверка уникальности**: номер ВУ — unique constraint в БД, блокирует повторную регистрацию даже с другого Telegram-аккаунта — тоже не требует SDK, чистая логика БД.
7. **Финальное решение по подлинности — за модератором**: карточка заявки в модерации (раздел 9) показывает фото документа, результат сверки ФИО и флаг эвристик редактирования одним экраном — человек принимает финальное решение «одобрить/отклонить», имея все автоматические сигналы перед глазами.

### Варианты OCR-провайдеров (текстовый слой)

| Провайдер | Плюсы | Цена (ориентировочно) |
|---|---|---|
| **Yandex Vision OCR** | Отличное качество на кириллице, простой REST API | ~150–300 ₸-эквивалент / 1000 запросов (биллинг в рублях, уточнить конвертацию/доступность оплаты из РК) |
| **Google Cloud Vision API** | Высокое качество, глобальная доступность, международный биллинг (проще оплатить из РК картой) | ~$1.5 / 1000 изображений |

**Рекомендация:** Google Cloud Vision как основной (проще с оплатой и доступностью из Казахстана), Yandex Vision как фолбэк/сравнение качества на кириллице во время пилота на реальных фото от заказчика.

### Путь эскалации, если бюджет позволит или мошенничество станет проблемой
Если после запуска окажется, что через ручную модерацию всё же проходит заметное число поддельных документов — это станет измеримым фактом (не догадкой), и тогда решение о покупке специализированного SDK будет обосновано конкретными цифрами, а не предположением на старте. Архитектурно OCR вынесен за интерфейс `services/ocr/base.py` — подключение Smart Engines/Regula в будущем не потребует переписывать остальную бизнес-логику (сверку ФИО, уникальность, модерацию).

## 9. Админ-панель

**Решение (обновлено):** веб-панель строится сразу, без промежуточного Telegram-режима — см. Фазу 5 и раздел 5. Ниже — описание того, что реализуется в первой (уже полноценной, не одноразовой) версии, и отдельно то, что осознанно отложено.

**Что видит администратор:**
- Дашборд: количество заявок по статусам.
- Таблица заявок с колонками: ФИО, телефон, город, статус, дата подачи; фильтры по статусу, городу, диапазону дат регистрации, поиск по ФИО/телефону.
- Карточка заявки: полные данные анкеты, фото документа (через подписанный временный URL из S3, не публичная ссылка), видео-плеер, OCR-данные (raw + распознанные поля) рядом с введёнными пользователем, `verification_flags` подсвечены.

**Статусы заявки** (без отдельного `reupload_requested` — см. упрощение в Фазе 5, «запросить заново» переиспользует существующие `pending_document`/`pending_video`):
- `draft` — анкета не завершена
- `pending_document` — ожидает фото ВУ (в том числе после запроса модератора переснять)
- `pending_ocr` — фото загружено, идёт распознавание
- `document_flagged` — расхождение/подозрение (кроме несовпадения ФИО — оно теперь не доходит до модерации, см. Фазу 3), нужна ручная проверка
- `pending_video` — ожидает видео-визитку (в том числе после запроса модератора переснять)
- `pending_moderation` — полный комплект, ожидает решения администратора
- `approved`
- `rejected`

**Действия администратора:**
- Одобрить / Отклонить (с причиной) / Запросить фото заново / Запросить видео заново
- Просмотр истории действий по заявке (`ModerationLog`)

**Отложено на потом (см. раздел 5, Фаза 9 — V2):**
- Экспорт выборки в CSV/Excel
- Рассылка новости/активности сегменту пользователей
- Управление ролями (super-admin создаёт учётки модераторов) + 2FA — в первой версии один общий admin-логин

## 10. Безопасность

- **Защита от повторной регистрации:** unique-constraints в БД на telegram_id, нормализованный номер телефона (E.164) и номер документа; проверка на каждом шаге (при старте регистрации и повторно после OCR).
- **Защита от спама:** throttling-middleware на уровне aiogram (лимит сообщений/действий на пользователя в единицу времени, Redis-счётчики), cooldown после нескольких неудачных попыток OCR, простая проверка «не бот» на старте (нажатие кнопки).
- **Логирование:** структурированные JSON-логи (structlog), маскирование PII (телефон/номер документа частично скрываются в логах), request-id для трассировки цепочки событий, отдельные уровни для бота/воркеров/админки.
- **Резервное копирование:** ежедневный pg_dump с шифрованием, хранение вне VPS (второй регион/провайдер), ретенция 14–30 дней, регулярная проверка восстановления из бэкапа; версионирование/бэкап файлового хранилища (S3 versioning или отдельная копия).
- **Хранение файлов:** приватный S3-бакет (не public-read), доступ только через подписанные временные URL для админки, видео/фото не раздаются напрямую по постоянной ссылке.
- **Защита персональных данных:** явное согласие пользователя на обработку ПДн на этапе регистрации (с фиксацией времени согласия), шифрование чувствительных полей на уровне приложения/БД (номер документа, телефон), ограничение доступа к БД, HTTPS everywhere, соответствие Закону РК «О персональных данных и их защите» (см. раздел 6 — открытый вопрос локализации данных на территории РК), политика хранения/удаления данных по запросу пользователя.
- **Секреты:** .env не коммитится, в проде — переменные окружения/Docker secrets, ротация токенов бота при компрометации.
